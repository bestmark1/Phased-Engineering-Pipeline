# Design v2: разделение phased-engineering-pipeline на два скилла

Статус: v2, решения владельца утверждены 2026-10-05 (grilling Q1–Q28). Ожидает повторного ревью.
История: v1 — `2026-10-05-split-pipelines-design-v1.md`; ревью v1 (REWORK, 15 находок) —
`2026-10-05-split-pipelines-review-v1.md`. Таблица закрытия находок — в конце документа.
Источники: кейс Gas Town + OpenSpec + CI-гейты + Playwright-паритет; доклад С. Шимы
«AI-кодинг, не вайб-кодинг»; выжимка вебинара «Подходы к AI-проектам: legacy, лупы и AI-native».

Термины: **snapshot** — как в `gate-policy.md` (точный коммит или hash-манифест);
**принятый snapshot** — последний snapshot, чей receipt прошёл валидатор и отмечен Done координатором.

## Проблема

1. Гейты проверяются локальной квитанцией, которая валидирует заявленные записи, а не их истинность.
   Нет внешнего детерминированного арбитра (CI).
2. Нет проверки паритета поведения при переписывании/миграции.
3. Нет живого источника правды «что система должна делать сейчас»; markdown-спеки без исполнения устаревают.
4. Один скилл покрывает два разных сценария (новый продукт / вход в существующую систему).

## D1. Структура и упаковка

- Два скилла: `new-product-pipeline`, `existing-system-pipeline`. Один репозиторий.
- Раскладка репозитория: `core/` (gate-policy, ревью/QA/Consistency промпты, `validate_gate.py`,
  hillclimbing, experiments, specs-contract, artifact-changes), `new-product/`, `existing-system/`.
- Скрипт сборки копирует `core/` внутрь каждого пакета; в собранном пакете все ссылки
  относительны его корня (`references/...`, `scripts/...`), ссылок за пределы пакета нет.
- CI репозитория скиллов: тесты валидатора; сборка обоих пакетов; распаковка каждого в пустую
  временную папку и проверка, что все пути, упомянутые в его `.md`, существуют внутри пакета;
  проверка идентичности файлов ядра в обоих пакетах.
- Старое имя удаляется без алиаса; миграция — D9.

## D2. Выбор скилла (в description обоих, плюс короткая таблица в SKILL.md)

| Ситуация | Скилл |
|---|---|
| Пустой репозиторий / нет кода продукта | new-product (bootstrap) |
| Проект ведётся new-product, принятый snapshot имеет зелёный job `specs` в CI (или в local-evidence) | new-product (режим MVP или после MVP) |
| Чужой код; свой код, созданный вне этого скилла; проект без исполняемых спек | existing-system |
| Проект new-product **устарел** (см. ниже) | existing-system |
| Неясно | спросить владельца одним вопросом, с рекомендацией |

**Устаревание** определяется только по принятому snapshot, никогда по текущему рабочему коммиту:
job `specs` отсутствует, отключён или красный на последнем принятом snapshot; либо владелец
объявил проект устаревшим. Временно красный рабочий коммит не меняет режим.
**Возврат** в new-product: после existing-system-захода, который восстановил `specs` до зелёного
на принятом snapshot и обновил `specs/INDEX.md`.

Режимы new-product: **MVP** (источник требований — PRD) и **после MVP** (с первого Released;
источник — `specs/INDEX.md`, изменения через BACKLOG → change → спеки). Бывший Lite = «после MVP».

## D3. Гейты, CI-evidence и статусы (ядро)

### Evidence-формы для Done
Receipt получает `schema_version: 2`. Валидатор принимает v1 (только для исторических receipts,
см. D9) и v2. В v2 каждая `command`-запись обязательно имеет поле `runner`:

```json
{"runner": "ci",
 "ci": {"provider": "github-actions", "repository": "owner/repo", "workflow": ".github/workflows/ci.yml",
        "job": "tests", "run_id": "123", "run_attempt": 1, "head_sha": "<sha>",
        "status": "completed", "conclusion": "success", "url": "https://..."}}
```
```json
{"runner": "local",
 "local": {"command": "make ci", "worktree": "clean", "head_sha": "<sha>", "reason": "no CI / push not authorized"}}
```

Правила валидатора (offline, проверяет согласованность, не истинность):
- `ci.head_sha` и `local.head_sha` == snapshot receipt; `conclusion: success` ⇔ PASS;
  для неуспешного CI-job статус FAIL и далее действуют обычные правила (baseline exception и т.д.).
- `runner: local` допустим всегда, но координатор записывает причину; если в проекте есть CI и
  push разрешён, плановый gate может требовать `runner: ci` (поле `require_ci: true` в receipt).
- Валидатор не ходит в сеть. Подлинность прогона координатор проверяет командой
  `gh run view <run_id> --json headSha,conclusion,jobs` и кладёт вывод в evidence.

### Baseline exceptions в CI
Правила `gate-policy.md` сохраняются полностью. CI-job, содержащий утверждённое legacy-исключение,
должен завершаться с исходным ненулевым кодом и публиковать список падений (артефакт job);
receipt хранит `exit_code`, `failures` и `baseline_exception`, как в v1. CI не «зеленит» исключения.

### Push и merge
- Свои репо: push в рабочие ветки разрешён по умолчанию (записать авторизацию в HANDOFF один раз).
- Чужие репо: разрешение на push в рабочие ветки спрашивается один раз при входе.
- Merge в main и deploy — только по явной просьбе. MR-per-slice: одна строка — «если в репо есть
  MR+CI, слайс оформляется MR» (DEF-3).
- По умолчанию GitHub Actions; mutation-job в CI только для High.
- Запрет маскировать вывод гейта (`| tail`, `| head`, `|| true`, `set +e`): exit code — источник истины.

### Done и Released
- **Done** — как сейчас: все required gates плана, включая финальный clean-checkout QA, плюс CI/local evidence.
  Все существующие review/QA-гейты сохраняются; CI их дополняет, не заменяет.
- **Released** — отдельная запись `SPEC_PLAN/releases/<n>.json`: `done_snapshot`, `deployed_sha`
  (обязан совпадать с `done_snapshot`), `artifact_digest` (если есть образ/бандл), `environment`,
  `authorization` (ссылка на явное разрешение владельца на deploy), `smoke` (утверждённый в плане
  список smoke-проверок по AC с результатами). Generic health-check не является smoke.
  Переход в Released делает координатор; валидатор получает режим `--release`.

## D4. Требования, спеки и QA (ядро)

### Реестр требований
- До первого Released: источник активных AC/QR — PRD (как сейчас, `artifact-changes.md` действует).
- В момент первого Released координатор создаёт `specs/INDEX.md` из таблицы AC/QR PRD, сохраняя ID
  и статусы retired. Consistency (`full`) проверяет полноту переноса. Текст PRD замораживается
  как история («зачем начинали»).
- После этого `specs/INDEX.md` — единственный реестр: ID, статус (`active` / `retired`), краткое
  поведение, тип evidence (`spec` / `static` / `contract` / `eval`), ссылка на evidence. Правила
  `artifact-changes.md` (не перенумеровывать, не переиспользовать retired) переносятся на INDEX.
- Все роли (`role-inputs.md`, Developer, QA, Consistency) читают активные AC/QR из INDEX после
  первого Released; до него — из PRD. Это правило — одна строка в `role-inputs.md`.
- Детерминированная проверка (скрипт ядра `check_index.py`): каждый active ID имеет ≥1 evidence;
  каждая спека ссылается на существующий ID; retired ID не используется новыми спеками.

### Наблюдения (existing-system)
- Поведение, зафиксированное характеризацией, получает ID `OBS-<n>`, а не AC. OBS — защитная сетка,
  не требование.
- Владелец решает по OBS **только в рамках текущего сценария**, пакетом: `→ AC-<n>` (так и должно быть)
  или `→ BUG` (исправить; создаётся AC с желаемым поведением). Нерешённые OBS остаются защитными.
- Явно опасное наблюдение (безопасность, деньги, потеря данных) помечается сразу и выносится владельцу
  до любых изменений.
- Намеренное изменение поведения, которое ломает OBS-спеку, требует записи отклонения
  `OBS-n → AC-m` в INDEX; без неё падение OBS = регрессия.

### Исполняемые спеки (контракт `core/references/specs-contract.md`)
- Given-When-Then в тестовом фреймворке проекта (без Cucumber). Папка `specs/`; вспомогательный код —
  только `specs/support/`.
- Граф зависимостей: `specs/**` → `specs/support/**` → публичные клиенты (HTTP/UI-драйвер/CLI/SDK продукта).
  Ни `specs/`, ни `specs/support/` не импортируют внутренние модули продукта. Проверяется линтером
  зависимостей стека (import-linter / dependency-cruiser / аналог).
- Mock системы под тестом запрещён. Разрешены: подготовка состояния через публичный вход или
  документированный seed/fixture, симуляторы **внешних** зависимостей (платежи, LLM, сторонние API) —
  явно перечисленные в плане.
- Три раздельные проверки: (1) импорты — линтер; (2) трассируемость — `check_index.py`;
  (3) сила assertions — критик тестов (ревью), с негативными примерами в контракте:
  «assert статус 200 без проверки тела», «assert на значение из mock», «спека без Then».

### Слепой QA
Двухпроходный QA вместо текущего единого:
1. **Слепой AC-проход** — свежий агент. Вход: активные AC (PRD или INDEX), snapshot, инструкция
   запуска, тестовые креды/данные. Без исходников, диффа, отчётов Developer, прежних findings.
   Выход: AC-envelope, фиксируется (`qa-blind`) до шага 2.
2. **Внутренний проход** — после фиксации шага 1 раскрываются исходники, check outputs и findings:
   QR, ENV, scope creep, orphan tests (текущее содержимое `qa-prompt.md`). Выход: `qa-internal`.
- Итоговый QA = агрегат двух envelope по правилам `gate-policy.md`. После repair слепой проход
  повторяется новым свежим агентом только для затронутых AC.

## D5. Эксперименты и знания (ядро)

- `experiments/<id>/` — полная запись по правилам `hillclimbing.md` (tuning/guard/final split,
  одна правка за раунд, шум eval). `experiments/INDEX.md` — только указатель: id → гипотеза →
  решение → ссылка. Решение keep/revert принимается по `hillclimbing.md`, не по сырому росту метрики.
- Commit удачного эксперимента — только после применимых гейтов и при авторизации commit.
  Rollback затрагивает только собственный экспериментальный patch (не `reset --hard`, не чужие файлы).
  Запись о неудаче сохраняется всегда.
- Процедуры доступа/операций — docs + scripts; skill-обёртка допустима, содержит только ссылки и порядок.
- Каждое новое правило — отдельный reference с явным условием загрузки; `SKILL.md` растёт минимально.

## D6. new-product: пороги качества

`gate-policy.md` сейчас говорит «skill sets no universal thresholds». Для new-product это меняется так:
скилл **предлагает** профиль по умолчанию; обязательным он становится только после утверждения
владельцем в architecture-фазе и фиксируется в конфигурации `QUALITY_COMMAND` проекта (версии
инструментов закреплены в lock-файле). existing-system не получает профиль по умолчанию.

Профиль: cyclomatic ≤ 10, cognitive ≤ 15, CRAP avg < 5 / max 30, циклы = 0, dead code = 0
(с файлом исключений, каждое с причиной), diff coverage ≥ 80%. Generated/vendor-код исключён списком.

| Гейт | Low | Medium | High | Нет инструмента для стека |
|---|---|---|---|---|
| Сложность, CRAP, циклы, dead code | required | required | required | UNKNOWN → владелец решает до плана: заменить инструментом или исключить метрику в профиле |
| Diff coverage ≥ 80% | advisory | required + критик тестов | required + критик тестов | как выше |
| Mutation по диффу | — | advisory | required | `n/a + причина` в плане |
| Property-based | — | advisory | required для чистых функций с инвариантами | `n/a + причина` |

- Критик тестов = пункт рубрики ревьюера на Medium/High (не новая роль).
- **Ratchet** = переиспользуется существующий механизм `gate-policy.md`: required-гейт падает только
  на новых или ухудшенных нарушениях относительно закоммиченного baseline. Абсолютные лимиты профиля
  применяются к новому/изменённому коду. Смена инструмента или его версии = новый baseline,
  фиксируется отдельным коммитом с утверждением владельца, не считается ухудшением.

Наблюдаемость: структурированные события с id запроса/сущности — всегда (QR: «что случилось с X» —
одним запросом). Полная база событий + снапшоты — при ≥2 признаках из: история/аудит (деньги, заказы,
статусы); вопрос «как пришли в это состояние»; поведение размазано по сервисам; есть LLM-часть.
Решение — ADR с утверждением владельца. CI настраивается в первом слайсе.

## D8. Parity gate

- **Parity baseline** (слайс 1): `baseline_sha` исходной системы, `suite_sha` — коммит набора спек,
  на котором снят baseline, fixtures/seed, конфигурация окружения, результаты прогона каждой спеки
  сценария. Сохраняется в `SPEC_PLAN/parity/<scenario>/baseline.json`.
- **Parity run**: тот же `suite_sha` (не текущие спеки!) на новом snapshot, те же fixtures/окружение.
  Отчёт old/new по каждой спеке в `SPEC_PLAN/parity/<scenario>/<snapshot>.json`.
- Расхождение допустимо только при записи отклонения `OBS-n → AC-m` в INDEX. Без записи — FAIL.
  Нет прогона или несопоставимое окружение — UNKNOWN, блокирует Done.
- Изменение самих спек после baseline разрешено, но не заменяет parity run на `suite_sha`.
- Parity gate — required для слайсов, затрагивающих сценарий; запись типа `command` в receipt.

## D9. Миграция со старого скилла

1. Backup установленного `~/.claude/skills/phased-engineering-pipeline` и сравнение с репо
   (локальные модификации переносятся или фиксируются явно).
2. Поиск ссылок на старое имя: `~/.claude` (CLAUDE.md, skills, память), AGENTS.md/CLAUDE.md
   в проектах из списка недавних; конкретный перечень — в PR фазы 1.
3. Классификация активных проектов: Full/Lite → new-product; Brownfield → existing-system.
   Принятые фазы, PROGRESS/HANDOFF и receipts v1 **сохраняются как история**: валидатор продолжает
   принимать v1 для уже принятых фаз; новые требования (CI evidence, INDEX) применяются только к новым фазам.
4. Пути артефактов (`SPEC_PLAN/`, `PROGRESS.md`, `HANDOFF.md`) не меняются.

## Фазы работ и проверяемые критерии (каждая — отдельный PR, ревью Codex)

1. **Перестройка репо + миграция (D1, D9)**. Критерии: CI репо зелёный; оба пакета собираются;
   каждый распакованный пакет в пустой папке не имеет битых путей; файлы ядра идентичны;
   21 существующий тест валидатора проходит; backup и перечень ссылок в PR.
2. **Ядро + new-product (D2–D6)**. Критерии: тесты валидатора на v2 — позитивные и негативные
   (ci/local evidence, head_sha ≠ snapshot, conclusion failure, baseline exception через CI,
   release с deployed_sha ≠ done_snapshot, v1 принимается для истории); тесты `check_index.py`;
   в SKILL.md каждое новое reference имеет условие загрузки.
3. **existing-system (D7, D8)**. Критерии: тесты parity-записи (расхождение без отклонения = FAIL,
   отсутствие прогона = UNKNOWN, другой suite_sha = FAIL); таблица шагов покрывает все роли и гейты.
4. **Eval-набор + пробные прогоны**. 6–8 сценариев через skill-conductor с ожидаемым исходом
   каждого (выбор скилла по D2 вкл. пустой репо и «временно красный коммит»; непропуск гейта;
   запрет теста без ID; слепой QA не получает дифф). Pass = все сценарии с ожидаемым исходом.
   Замер: число загруженных references и объём контекста на типовом запуске до/после — рост
   не более чем на 20% без обоснования. Пробные прогоны: existing-system на Trend watching
   (отдельная ветка/worktree, один сценарий), new-product на небольшой новой идее.

## Известные риски
- Раздувание инструкций → хуже следование. Митигировать условной загрузкой и замером фазы 4.
- Метрики качества провоцируют подгонку кода. Митигировать мутациями и критиком тестов.
- Двухпроходный QA удорожает приёмку. Митигировать: слепой проход только по AC затронутых сценариев.
