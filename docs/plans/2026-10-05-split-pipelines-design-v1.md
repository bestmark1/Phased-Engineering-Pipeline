# Design: разделение phased-engineering-pipeline на два скилла

Статус: утверждено владельцем 2026-10-05 (grilling-сессия), до ревью плана.
Источники: кейс Gas Town + OpenSpec + CI-гейты + Playwright-паритет; доклад С. Шимы
«AI-кодинг, не вайб-кодинг» (agent-coding-talk.pages.dev); выжимка вебинара «Подходы к
AI-проектам: legacy, лупы и AI-native» (Ринат, Агис, июль 2026).

## Проблема

1. Гейты проверяются локальной квитанцией (`validate_gate.py`), которая валидирует заявленные
   доказательства, а не их истинность. Нет внешнего детерминированного арбитра (CI).
2. Нет проверки паритета поведения при переписывании/миграции.
3. Артефакты (PRD, архитектура) пишутся под инициативу; нет живой спеки системы «как есть».
   Markdown-спеки без исполнения устаревают (аргумент Агиса).
4. Один скилл покрывает два разных по природе сценария: новый продукт и вход в существующую
   систему. Это размывает триггер и раздувает контекст.

## Решения

### D1. Структура
- Два скилла: `new-product-pipeline`, `existing-system-pipeline`. Один репозиторий.
- Общее ядро (gate-policy, роли ревью/QA, `validate_gate.py`, hillclimbing, experiments)
  хранится в одном месте; скрипт сборки кладёт его в оба `.skill`-пакета.
- CI репозитория скиллов: тесты валидатора + проверка идентичности копий ядра в пакетах.
- Старое имя `phased-engineering-pipeline` удаляется без алиаса; ссылки на него
  (README, AGENTS.md проектов, память) находятся и обновляются.

### D2. Правило выбора скилла (в description обоих)
- `new-product-pipeline`: проект создан этим скиллом и его артефакты живые
  (PRD/спеки, PROGRESS, CI зелёный). Режимы: **MVP** (по PRD) и **после MVP**
  (BACKLOG.md → change proposal → обновление спек). Нынешний Lite = режим «после MVP».
- `existing-system-pipeline`: всё остальное — чужой код, свой старый код без живых спек,
  проект с устаревшими артефактами.
- Проект, чьи исполняемые спеки перестали проходить/поддерживаться, переходит в existing-system.

### D3. Общее ядро — гейты и статусы
- Done слайса = зелёный CI на точном SHA; ссылка на прогон в gate receipt; валидатор
  проверяет наличие записи (без сетевого доступа).
- Push в рабочие ветки: в своих репо — по умолчанию; в чужих — разрешение один раз при входе.
  Merge в main и deploy — только по явной просьбе.
- Fallback без CI/без разрешения на push: та же команда, что в CI (`make ci` или эквивалент),
  в чистом worktree точного коммита.
- По умолчанию GitHub Actions. Mutation testing в CI — только на глубине High (стоимость минут).
- Два статуса: **Done** (гейты приняты) и **Released** (разрешённый deploy + smoke на реальном
  окружении; Mac ≠ Linux).
- Запрет маскировать вывод гейта (`| tail`, `| head`, `|| true`): exit code — источник истины.

### D4. Общее ядро — QA и спеки
- Слепой QA для AC: вход — спека/PRD, коммит, инструкция запуска. Дифф и отчёт Developer
  доступны только после вердикта. QR, требующие внутренних проверок, — не слепые.
- Живая спека = исполняемые Given-When-Then спеки черного ящика в тестовом фреймворке проекта
  (без Cucumber) + короткий md-указатель.
  - Лежат в `specs/`; обращаются к системе только через публичный вход (HTTP/UI/CLI).
  - Импорт внутренностей запрещён линтером зависимостей (import-linter / dependency-cruiser
    или аналог стека).
  - Каждая спека ссылается на AC/QR ID.
- До первого релиза источник правды — PRD; после — PRD заморожен, изменения идут через
  BACKLOG → change → спеки.

### D5. Общее ядро — эксперименты и знания
- `experiments/` + `experiments/INDEX.md` (одна строка: гипотеза → baseline → score → решение).
  Улучшил метрику — commit; ухудшил — rollback кода, запись остаётся. Расширение `hillclimbing.md`.
- Процедуры доступа/операций живут как docs + scripts; skill-обёртка допустима, но содержит
  только ссылки и порядок вызова, без собственного знания.
- Каждое новое правило — отдельный reference с условием загрузки; `SKILL.md` почти не растёт.

### D6. new-product-pipeline
- Пороги качества (профиль по умолчанию, предлагает архитектор, утверждает владелец,
  дальше только ужесточение/ratchet): CRAP avg < 5 / max 30, cyclomatic ≤ 10,
  cognitive ≤ 15, diff coverage ≥ 80%, циклические зависимости = 0.
  Включаются только вместе с mutation testing и критиком тестов (защита от Goodhart).
- Mutation + property-based тесты по диффу на High; на Medium — рекомендация.
  Нет инструмента для стека → `n/a + причина`, не молчаливый пропуск.
- Наблюдаемость: структурированные события с id запроса/сущности — всегда (QR: агент отвечает
  «что случилось с X» одним запросом). Полная база событий + снапшоты — если выполнено ≥2 из:
  история/аудит (деньги, заказы, статусы); вопрос «как пришли в это состояние»; поведение
  размазано по нескольким сервисам; есть LLM-часть (события = сырьё для evals/симуляций).
  Решение — ADR с утверждением владельца.
- CI настраивается в первом слайсе.

### D7. existing-system-pipeline (по Ринату, скоуп — один сценарий за заход)
0. Карта процесса (красное — дорогая ошибка, синее — уходит время) → выбор одного сценария
   и глубины проверок по зонам.
1. AGENTS.md (короткий: что за проект, где docs и outline, как запустить, sibling-проекты,
   запреты) + `docs/surprises.md`. Запись в чужой репо — разрешение один раз при входе.
2. Read-only археология зон риска: авторизация, интеграции, платежи, деплой, cron, хардкоды,
   ENV. Опционально одноразовый интерактивный HTML-отчёт.
3. Процедуры доступа (БД, логи, CI) — только read-only учётки, которые настраивает владелец;
   секреты не попадают в чат/промпты.
4. Smoke + GWT-спеки текущего поведения сценария (характеризация).
5. Golden set + eval, если в сценарии алгоритм или LLM.
6. Изменение через слайсы и гейты ядра.
7. Паритет: те же спеки на новой версии; расхождение без ссылки на AC = регрессия;
   нет сравнения = UNKNOWN.
8. Ретро + разбор прошлых сессий агента (если есть транскрипты).
- Полное переписывание — серия сценариев (strangler fig), паритет растёт поэтапно.
- Окружение: Docker Compose / devcontainer; Nix — только если уже есть.

## Отложено (обязательно вернуться)

| ID | Что | Куда | Условие возврата |
|---|---|---|---|
| DEF-1 | Аварийный режим «ничего не трогай, найди причину» | отдельный скилл | после фазы 4 |
| DEF-2 | OpenSpec-адаптер (proposal/design/tasks ↔ наши артефакты) | existing-system | после пробного прогона existing-system; сверить актуальную CLI OpenSpec |
| DEF-3 | MR-per-slice как полноценный режим (сейчас одна строка) | ядро | если появится командная работа или Gas Town-оркестрация |

## Порядок работ (каждая фаза — отдельный PR, ревью Codex)

1. Перестройка репо: ядро, два скилла, скрипт сборки, CI репо.
   Критерий: оба пакета собираются; CI зелёный; тесты валидатора проходят; копии ядра идентичны.
2. new-product: D3–D6.
   Критерий: валидатор требует CI-ссылку для Done; references загружаются по условиям.
3. existing-system: D7.
   Критерий: пайплайн шагов 0–8 описан; паритет и GWT-правила в ядре используются, не дублируются.
4. Eval-набор (6–8 сценариев через skill-conductor: выбор скилла, непропуск гейта, запрет теста
   без требования и т.п.) + пробные прогоны: existing-system на Trend watching (отдельная ветка/
   worktree, один сценарий), new-product на небольшой новой идее.

## Известные риски
- Раздувание инструкций → агент хуже следует правилам. Митигировать условной загрузкой
  и eval-набором до/после.
- Метрики качества провоцируют подгонку кода. Митигировать мутациями и критиком тестов.
- Граница выбора скилла может оказаться нечёткой на практике — проверяется eval-сценариями.
